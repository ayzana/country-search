# Country Search — Design Document

## 1. Отмена устаревших запросов

### Проблема

Пользователь вводит `sp`, затем быстро дописывает `ain`. Сервер на `sp` отвечает медленнее, чем на `spain`. Без отмены ответ на `sp` прилетит позже и перезапишет корректный результат по `spain` — на экране окажутся данные не для того запроса, который сейчас в поле ввода. Это классическая гонка (race condition), и она воспроизводится стабильно при network throttling.

### Решение: `AbortController` на каждом вводе

В обработчике `input` (а **не** внутри debounce-колбэка) выполняется:

```ts
controller?.abort();
controller = null;
debouncedSearch.cancel();
```

Ключевой момент: отмена происходит на каждом изменении ввода, а не только когда debounce фактически запускает новый сетевой запрос. Иначе за время ожидания debounce (350 мс) устаревший ответ успеет прилететь и отрендериться под уже новым текстом.

Различение AbortError и TimeoutError
Оба приходят как DOMException, но с разными name:

AbortError — наша собственная отмена (новый ввод, очистка поля). Это не ошибка, пользователю ничего не показываем.

TimeoutError — истёк AbortSignal.timeout(ms). Это настоящая ошибка, показываем сообщение с кнопкой «Повторить».

Композиция двух источников отмены в один сигнал:

ts
AbortSignal.any([userSignal, AbortSignal.timeout(ms)])
userSignal отменяется по вводу, timeout — по времени. Какой сработал первым, тот и определит name ошибки. В catch — отдельные ветки:

ts
if (kind === 'abort') return; // тихо
if (kind === 'timeout') showError(...); // ошибка
if (kind === 'http') showError(...); // ошибка
if (kind === 'network') showError(...); // ошибка

## 2. Задержка debounce — 350 мс

300–400 мс — эмпирически оптимальный диапазон для поиска: человек успевает допечатать слово, но не чувствует задержки. 350 мс — середина диапазона.

Что будет, если убрать debounce
Каждый символ → отдельный запрос. При вводе «united states» это 13 запросов, из которых полезен только последний. Даже с AbortController это лишние соединения и риск упереться в rate limit API.

Что будет, если сильно увеличить (например, 2000 мс)
Пользователь печатает «spain», ждёт две секунды — интерфейс выглядит сломанным. При медленном наборе debounce будет сбрасываться постоянно, и запрос не уйдёт вообще, пока человек не остановится.

Почему отмена не ждёт debounce
abort() вызывается синхронно в input, а debounce откладывает запуск нового запроса. Это разные вещи: отмена должна быть немедленной, иначе устаревший ответ успеет прилететь за 350 мс ожидания.

## 3. Сложность (Big O)

mapCountryResponse(raw)
O(k), где k — число языков в raw.languages. Остальные поля (name, flag, capital, region, population) маппятся за O(1). Доминирует .map() по массиву языков. Для типичной страны k ≤ 3, то есть фактически константа.

mapCountryDetails(raw)
O(k + m), где k — число языков, m — число валют. Оба массива проходятся один раз. borders копируется как есть (O(b), где b — число границ, обычно ≤ 15).

SearchCache.get(query, signal)
Проверка кэша: O(1) — Map.get по строковому ключу.

Проверка «в полёте»: O(1) — второй Map.get.

Дедупликация: O(1) — если запись есть, возвращаем её промис, не создавая новый.

Итог: O(1) на каждый вызов get, независимо от размера кэша.

Почему Map, а не объект
Map даёт гарантированный O(1) на get/set/has/delete и не имеет проблемы прототипного наследования (ключ "constructor" не сломает кэш). Для строковых ключей-запросов это важно.

## 4. Принципы чистого кода

Single Responsibility Principle
debounce — только управление таймером, ничего не знает о поиске.

searchCountries — только сетевой запрос + проверка response.ok, не знает о DOM.

mapCountryResponse / mapCountryDetails — чистые функции маппинга, без побочных эффектов.

classifyError — только классификация, без рендера.

Каждая функция тестируется изолированно, без браузера и реальной сети.

Чистые функции (mapCountryResponse, mapCountryDetails, classifyError)
Не мутируют вход, не зависят от глобального состояния, детерминированы. В тестах проверяется structuredClone входного объекта до и после — гарантия отсутствия мутаций.

Dependency Inversion (неявно)
searchCountries принимает signal как аргумент, а не создаёт его внутри. Это позволяет тестам подсунуть управляемый AbortController и проверить отмену. SearchCache.get тоже принимает signal снаружи — у каждого вызывающего свой сигнал, отмена одного не рушит общий промис.

Обработка ошибок через типизацию
classifyError возвращает ErrorKind — union из пяти строк. Это делает switch/if в catch исчерпывающим: TypeScript подскажет, если добавить новый вид ошибки и забыть ветку.

## 5. Бонус: кэш и дедупликация

Кэш по строке запроса
Map<string, Country[]>, ключ — query.toLowerCase(). Повторный запрос (пользователь стёр и напечатал то же самое) берётся из кэша, в сеть не уходит. Кэш не инвалидируется по времени — для стран это допустимо, данные меняются редко.

Дедупликация «в полёте»
Если на момент повторного запроса с тем же текстом уже есть запрос в полёте — возвращаем тот же промис, второй не создаём. Это Map<string, InflightEntry>, где InflightEntry содержит промис, внутренний AbortController и счётчик refs.

Отмена одного вызывающего не рушит общий промис
Ключевая тонкость: если два вызывающих ждут один промис, и первый отменяет свой сигнал — второй должен продолжить ждать. Реализация:

У InflightEntry свой внутренний AbortController, не связанный с сигналами вызывающих.

Каждый вызывающий «отписывается» через Promise.race([entry.promise, abortPromise]), где abortPromise отклоняется по его сигналу.

Счётчик refs: при refs === 0 внутренний контроллер отменяет сетевой запрос — никто больше не ждёт.

Так отмена первого вызывающего отклоняет только его промис, а entry.promise продолжает жить для второго.

Big O кэша с дедупликацией
get из кэша: O(1).

get из «в полёте»: O(1).

Создание новой записи: O(1) (два Map.set).

Итог: O(1) на вызов, память — O(n), где n — число уникальных запросов.

## 6. Обработка 404

countries.dev отвечает 404, когда совпадений нет. Это не ошибка, а пустой результат:

ts
if (res.status === 404) return [];
Любой другой неуспешный статус (500, 502, 503) → HttpError, который показывается пользователю с кнопкой «Повторить». Разделение важно: «ничего не найдено» — дружелюбное состояние, «ошибка сервера» — повод повторить.

response.ok проверяется вручную, потому что fetch не бросает исключение на HTTP-ошибках — это распространённое заблуждение. Без явной проверки !res.ok приложение попытается распарсить HTML-страницу ошибки как JSON и упадёт с невнятным SyntaxError.

## 7. Тестирование

TDD и порядок коммитов
Для каждой обязательной функции — пара коммитов: test: (красный) → feat: (зелёный). Husky pre-push запускает npm test и блокирует пуш красных тестов, поэтому пары уходят в один push. pre-commit запускает только lint-staged — иначе нельзя закоммитить красный тест (первый шаг TDD).

FIRST
Fast — все тесты на fake timers и моках, без реальной сети, выполняются за миллисекунды.

Isolated — restoreMocks: true и unstubGlobals: true в vitest.config.ts гарантируют, что мок fetch из одного теста не протекает в другой.

Repeatable — нет зависимости от времени, сети, порядка запуска.

Self-validating — expect(...).toBe(...), без ручной проверки вывода.

Timely — тесты пишутся до реализации.

Тест на гонку
Мок fetch обязан реагировать на signal и отклонять промис с AbortError при abort() до резолва. Иначе тест не отличит настоящую отмену от простого игнорирования устаревшего ответа. В тесте:

sp резолвится через 100 мс, spain — через 10 мс.

sp отменяется до своего резолва.

Проверяется: p1 отклонён с AbortError, p2 вернул Spain, в результате нет STALE.

Второй тест проверяет, что мок действительно отклоняет промис при abort() — иначе первый тест мог бы пройти по ложной причине.
